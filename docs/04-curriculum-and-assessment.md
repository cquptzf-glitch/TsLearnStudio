# TsLearnStudio 课程大纲与自动评测设计

- 版本：v0.2（目录基线；细节见第 9 节）
- 目标：从 C++/Qt 开发者过渡到能阅读、修改、调试 AI 生成的 TS/Web/React/Node 代码
- 总量：6 阶段、48 课；每课约 30–60 分钟，实践时间建议 ≥ 60%
- 课程生产要求：每一课必须包含目标、先修、概念、C++ 对比、可运行实例、动手作业、测试、复盘，不得只填标题

## 2. 单课统一结构与内容质量

每节课严格按如下顺序：
1. 目标和前置知识（完成后能做什么）。
2. 概念解释（正确术语与行为边界）。
3. C++/Qt 对比（相似点与不等价之处，如 TS 类型擦除）。
4. 执行过程演示（动画步骤和可观察输出）。
5. 讲解示例（可复制到练习区运行）。
6. 预测题（先判断结果，后显示解释）。
7. 动手编码（可重置的 starter、公开测试）。
8. 自动评测（明确失败断言和错误类型）。
9. 常见错误与复盘（为什么错，以及关联概念）。
10. 扩展挑战（可选，不影响必修完成）。

每课正文必须包含不少于一个正例、一个反例和一条「AI 常见错误」；难度依赖课程目标，不用固定字数充数。

## 4. 练习类型与自动评测

| 类型 | 评测手段 | 学生获得的反馈 |
| --- | --- | --- |
| 单选/多选/预测 | 确定答案与解释 | 知识点和易错原因 |
| 函数编码题 | TS typecheck + 公开/隐藏断言 | 输入、期望、实际、异常 |
| 缺陷修复题 | 回归测试 + 指定失败用例 | 缺陷位置与失败路径 |
| DOM 练习 | DOM 结构与事件行为断言 | 具体选择器和操作失败 |
| React 组件题 | 渲染与交互测试 | 组件行为与状态变化 |
| Node API 题 | HTTP 集成测试 | 状态码、响应体、异常 |
| 综合项目 | 分阶段里程碑检查 | 已完成/未完成需求清单 |

评测应按错误类别拆分：编译错误、运行错误、断言失败、超时、环境故障、测试工具故障。工具故障不能算作学生作业错误。

### 4.1 评分草案
- 正确性 60%：行为断言/业务验收；
- 边界及错误处理 20%：异常、空值和非法输入；
- 类型/静态质量 10%：严格 TS 检查与必要约束；
- 测试/可维护性 10%：自测与基本代码质量；
- 分数只是学习反馈，**通过判定以必测用例与关键门槛为准**；有关键用例失败不能仅凭总分通过。
- 对部分题目采用二元判定（通过/待修正），无需强行打分。

### 4.2 掌握度（启发式）
- 已读、练习通过、能独立重做、间隔复习通过分别记录；
- 连续失败表明需要复习，但不要使用未经验证的统计模型声称精准预测水平；
- 不记录敏感个人信息；复习推荐只使用本地题目结果。

### 4.3 公开测试与隐藏测试
本地离线产品中的隐藏测试文件不能保证对用户真正保密；隐藏仅表示 UI 默认不展示，以减少直接照抄。不要构建错误的“防作弊”安全假设。

## 5. 示例课程 TS-ASYNC：fetch 错误处理

**学习目标：** 解释 fetch 的网络拒绝与 HTTP 错误响应的区别，正确处理 response.ok、JSON 解析和取消。

**先修：** Promise、async/await、联合类型。

**概念重点：**
- await 对当前 async 函数挂起，不会阻塞整个 JS 事件循环。
- fetch 遇到 HTTP 404/500 通常仍 fulfilled；应检查 response.ok。
- 网络层错误可使 Promise rejected；JSON 解析也可能抛错。
- 强制转换为 TS 类型不是运行时数据校验；需要 schema 检查或类型守卫。

**starter：**
~~~typescript
type User = { id: number; name: string };

export async function loadUser(id: number): Promise<User> {
  const response = await fetch("/api/users/" + id);
  return response.json() as Promise<User>;
}
~~~

**目标：** 处理 200 有效 JSON、404/500 状态、网络异常和无效 JSON，向调用方提供可区分的错误；不修改函数名和入参签名。

**公开测试：**
1. 200 JSON 返回期望对象；
2. 404 返回或抛出可辨识的 HTTP 错误；
3. 500 不当作成功用户数据；
4. 网络拒绝能被正确传播或包装；
5. 返回体格式不合法应拒绝（需定义验证规则）。

**动画：** 点击“发送请求”→ pending → fulfilled(Response 404) → response.ok=false → 错误处理；对照网络拒绝时的 rejected 分支。

**自检思考：** 既然 fetch 的 Promise fulfilled，为什么业务仍失败？

## 6. 综合项目：Mini TestPilot

模块任务与验收：
- M1 数据模型：TestCase 类型、状态联合类型和输入校验。
- M2 后端：GET/POST/PATCH/DELETE，正确状态码，SQLite 事务。
- M3 React 列表：加载/空/错误状态、搜索筛选。
- M4 新增编辑：表单校验、乐观/保守更新策略与反馈。
- M5 测试：前后端关键路径单测、API 集成测试。
- M6 Debug：提供两处真实缺陷，要求通过调试工具定位修复。
- M7 审查：解释所修改代码、影响范围、回归测试。
- M8 毕业：提供项目总结和已验证能力清单。

完成后的产物应当是可运行的本地全栈项目，能从程序导出并交给 VS Code 接续开发。
